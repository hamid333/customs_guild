# سایت انجمن صنفی حق‌العمل‌کاران گمرکی (Django — چند-اپی)

پروژه‌ای کامل با جنگو برای انجمن صنفی حق‌العمل‌کاران گمرکی. این پروژه به‌صورت **چند اپ مستقل**
(یک اپ برای هر بخش) ساخته شده تا هر بخش مدل، ویو، فرم، URL و قالب‌های خودش را داشته باشد و
توسعه/نگهداری هرکدام مستقل از بقیه باشد.

## اپ‌ها

| اپ | مسئولیت | وابستگی |
|---|---|---|
| `core` | صفحه‌ی اصلی، ورود/خروج داشبورد، نمای کلی داشبورد، مدیریت کاربران و دسترسی بخش‌ها، میکسین‌های مشترک | — |
| `specializations` | مدل «زمینه‌ی فعالیت» (قابل افزودن دستی) | — |
| `members` | اعضای صنف (نام، سمت: عادی/مدیرعامل/بازرس/دیگر، زمینه‌های فعالیت) | `specializations` |
| `hscodes` | جست‌وجو و مدیریت ردیف‌های تعرفه‌ی گمرکی (HS Code) | — |
| `news` | اخبار سایت (تاریخ انتشار شمسی) | — |
| `works` | کارهای انجام‌شده / نمونه‌کارها (تاریخ اتمام شمسی) | `members` |
| `contact` | فرم و پیام‌های «تماس با ما» | — |
| `sliders` | اسلایدهای صفحه‌ی اصلی (تمام فیلدها اختیاری: eyebrow/title/desc/image/دکمه) | — |

هر اپ (به‌جز `core`) الگوی یکسانی دارد:
`models.py`, `admin.py`, `forms.py`, `views.py`, `urls.py`, `migrations/0001_initial.py`,
و `templates/<app>/...` (صفحات عمومی در ریشه، صفحات داشبورد در `dashboard/`، و فرم‌های داخل
مودال در `dashboard/fragments/_*.html`).

منطق مشترک بین همه‌ی اپ‌ها (نیازمند staff بودن + دسترسی به بخش + مودال SweetAlert2 برای
افزودن/ویرایش/حذف) در `core/mixins.py` قرار دارد و همه‌ی اپ‌های دیگر از آن استفاده می‌کنند.

هویت بصری: رنگ اصلی سورمه‌ای (`#0b1a2e`)، رنگ مکمل طلایی کهنه (`#c9a94e`) و مسی (`#b87333`).

## ویژگی‌ها

- صفحه‌ی اصلی با اسلایدر تمام‌صفحه که کاملاً از داشبورد قابل مدیریت است.
- صفحه‌ی «اعضای اصلی» و صفحه‌ی «همه‌ی اعضا» (جست‌وجو + فیلتر بر اساس زمینه‌ی فعالیت). با کلیک
  روی تصویر/نام هر عضو، صفحه‌ی مجزای پروفایل او باز می‌شود.
- هر عضو دارای سمت مشخص است: کاربر عادی، مدیرعامل، بازرس یا شخص دیگر.
- **سوابق فعالیت هر عضو با ویرایشگر متن غنی CKEditor** قابل طراحی است (تیتر، لیست، رنگ،
  نقل‌قول، تصویر، جدول و ...) و در صفحه‌ی پروفایل همان عضو به‌صورت زیبا نمایش داده می‌شود.
- جست‌وجوی ردیف تعرفه‌ی گمرکی (HS Code)، اخبار (+ نوار اخبار فوری)، نمونه‌کارها، تماس با ما.
- **افزودن/ویرایش/حذف همه‌ی بخش‌های داشبورد از طریق مودال SweetAlert2** (بدون رفتن به صفحه‌ی جداگانه).
- انتخاب‌گرهای چندگزینه‌ای با **Select2** (جست‌وجوپذیر، RTL).
- ورود تاریخ (تاریخ اتمام کار، تاریخ انتشار خبر) با **تقویم شمسی** (`django-jalali` + `persian-datepicker`).
- **مدیریت کاربران داشبورد با دسترسی دقیق و جزئی**: برای هر کاربر، به‌ازای هر بخش داشبورد
  (اعضا/زمینه‌های فعالیت/اسلایدر/اخبار/نمونه‌کارها/تعرفه‌ها/پیام‌های تماس/مدیریت کاربران)
  می‌توانید هرکدام از چهار عملیات «افزودن، ویرایش، نمایش، حذف» را جداگانه فعال/غیرفعال کنید
  (مثلاً کاربری فقط بتواند اخبار را ببیند و ویرایش کند اما حذف نکند). مدیر کل (superuser)
  همیشه به همه‌چیز دسترسی کامل دارد.
- **بخش‌های داشبورد به‌صورت خودکار کشف می‌شوند**: کافی است در `apps.py` اپ جدید
  `dashboard_section = True` را ست کنید؛ بدون هیچ تغییر دیگری، آن اپ در فهرست بخش‌های
  قابل‌دسترس (هم در سایدبار و هم در فرم دسترسی کاربران) ظاهر می‌شود.
- پنل ادمین جنگو (`/admin/`) به‌عنوان مسیر مدیریتی جایگزین/مکمل (با ویجت تقویم شمسی).

## پیش‌نیازها

- Python 3.10 یا بالاتر و pip
- **اتصال اینترنت در مرورگر** برای بارگذاری کتابخانه‌های CDN داشبورد: jQuery، Select2،
  SweetAlert2 و persian-datepicker (این‌ها از CDN بارگذاری می‌شوند، نه از خود پروژه). CKEditor
  خودش از طریق پکیج `django-ckeditor` سرو می‌شود و به CDN نیاز ندارد.
  برای کار آفلاین با بقیه، آن فایل‌ها را دانلود کرده و در `core/static/core/vendor/` قرار دهید و
  لینک‌های CDN را در `core/templates/core/dashboard/base_dashboard.html` به مسیر محلی تغییر دهید.

## نصب و اجرا (محیط توسعه)

```bash
# 1) ساخت و فعال‌سازی محیط مجازی
python3 -m venv .venv
source .venv/bin/activate        # ویندوز: .venv\Scripts\activate

# 2) نصب وابستگی‌ها (شامل Django، Pillow و django-jalali)
pip install -r requirements.txt

# 3) اجرای مایگریشن‌ها (ساخت پایگاه‌داده‌ی SQLite)
python manage.py migrate

# 4) ساخت کاربر مدیر کل (superuser) برای ورود به داشبورد و پنل ادمین
python manage.py createsuperuser

# 5) (اختیاری اما پیشنهادی) پرکردن پایگاه‌داده با داده‌ی نمونه برای تست سریع
#    این دستور یک کاربر محدود نمونه هم می‌سازد: news-editor / editor12345
#    (فقط دسترسی به بخش‌های «اخبار» و «کارهای انجام‌شده»)
python manage.py seed_data

# 6) اجرای سرور توسعه
python manage.py runserver
```

سپس:
- سایت عمومی: http://127.0.0.1:8000/
- اعضای اصلی: http://127.0.0.1:8000/members/featured/
- داشبورد مدیریتی: http://127.0.0.1:8000/dashboard/login/
- مدیریت کاربران و دسترسی‌ها (فقط مدیر کل یا کاربر دارای دسترسی «users»):
  http://127.0.0.1:8000/dashboard/users/
- پنل ادمین جنگو: http://127.0.0.1:8000/admin/

برای ورود به داشبورد، کاربر باید `is_staff=True` باشد. برای دیدن هر بخش از داشبورد، کاربر
باید یا `is_superuser=True` باشد یا از صفحه‌ی «کاربران و دسترسی‌ها» به آن بخش دسترسی گرفته باشد.

## مدیریت کاربران و دسترسی دقیق بخش‌ها

صفحه‌ی داشبورد → «کاربران و دسترسی‌ها» (`/dashboard/users/`) امکانات زیر را می‌دهد:

- **افزودن کاربر جدید**: نام کاربری، ایمیل، رمز عبور و مشخص‌کردن مدیر کل بودن یا نبودن.
- **ماتریس دسترسی**: در همان فرم افزودن/ویرایش، جدولی نمایش داده می‌شود که سطرهای آن بخش‌های
  داشبورد (اعضا، زمینه‌های فعالیت، اسلایدر، اخبار، نمونه‌کارها، ردیف‌های تعرفه، پیام‌های تماس،
  مدیریت کاربران) و ستون‌های آن چهار عملیات «افزودن، ویرایش، نمایش، حذف» هستند. یعنی می‌توانید
  مثلاً به یک کاربر فقط اجازه‌ی «نمایش و ویرایش اخبار» بدهید بدون اینکه بتواند خبری حذف کند یا
  به بخش‌های دیگر اصلاً دسترسی داشته باشد.
- فقط بخش‌هایی که کاربر حداقل دسترسی «نمایش» به آن‌ها دارد در سایدبار داشبوردش ظاهر می‌شوند؛
  و هر عملیات (دکمه‌ی افزودن/ویرایش/حذف) هم روی سرور دقیقاً همان مجوز را چک می‌کند — پنهان‌کردن
  دکمه در قالب صرفاً یک کمک بصری است، اصل کنترل دسترسی سمت سرور انجام می‌شود.
- کاربران «مدیر کل» (`is_superuser=True`) صرف‌نظر از ماتریس، همیشه به همه‌چیز دسترسی دارند.
- کاربر نمی‌تواند حساب خودش را حذف کند.

این منطق در `core/models.DashboardAccess` (یک JSON از شکل
`{"members": ["view", "edit"], "news": ["view", "add", "edit", "delete"], ...}`)
و `core/mixins.SectionAccessRequiredMixin` پیاده‌سازی شده؛ هر ویوی داشبورد در هر اپ با
ست‌کردن `required_section = "..."` و `required_action = "view"/"add"/"edit"/"delete"`
به این سیستم متصل می‌شود.

### افزودن اپ جدید به سیستم دسترسی‌ها (خودکار)

فهرست بخش‌های قابل‌دسترس (`core.models.get_dashboard_sections()`) به‌صورت خودکار از روی
اپ‌های نصب‌شده ساخته می‌شود؛ کافی است در `apps.py` اپ جدید، مشابه اپ‌های دیگر، این خط را
اضافه کنید:

```python
class MyNewAppConfig(AppConfig):
    name = "my_new_app"
    verbose_name = "عنوان فارسی بخش"
    dashboard_section = True   # همین یک خط کافی است
```

با این کار، «عنوان فارسی بخش» به‌طور خودکار هم در سایدبار (در صورت داشتن دسترسی) و هم در
ماتریس دسترسی صفحه‌ی «کاربران» ظاهر می‌شود — نیازی به تغییر `core/models.py` یا هیچ فایل
دیگری نیست. برای این‌که ویوهای داشبورد آن اپ هم واقعاً کنترل شوند، همان الگوی بقیه‌ی اپ‌ها را
دنبال کنید: `SectionAccessRequiredMixin` را با `required_section = "my_new_app"` (اسلاگ
همان app_label) و `required_action` مناسب هر ویو (view/add/edit/delete) استفاده کنید.

## نحوه‌ی کار مودال‌های افزودن/ویرایش/حذف (SweetAlert2)

هر دکمه‌ی «افزودن»/«ویرایش» در داشبورد یک `data-modal-form` با `data-url` به آدرس ثبت/ویرایش دارد.
با کلیک روی آن، `core/static/core/js/dashboard.js` فرم را به‌صورت AJAX از همان ویوی جنگو می‌گیرد و
داخل یک مودال SweetAlert2 نمایش می‌دهد؛ ثبت فرم هم از طریق همان مودال و AJAX انجام می‌شود.
دکمه‌های «حذف» هم با `data-modal-delete` یک تأییدیه‌ی SweetAlert2 نشان می‌دهند. تمام ویوهای
Create/Update/Delete داشبورد (در هر اپ) از میکسین‌های `AjaxFormMixin` / `AjaxDeleteMixin` در
`core/mixins.py` استفاده می‌کنند و همچنان به‌صورت صفحه‌ی کامل (fallback بدون جاوااسکریپت) هم
قابل استفاده‌اند.

## نکات مهم پیش از انتشار (Production)

1. مقدار `SECRET_KEY` در `customs_guild/settings.py` را با یک کلید تصادفی و محرمانه جایگزین کنید.
2. `DEBUG = False` کنید و `ALLOWED_HOSTS` را به دامنه‌ی واقعی محدود کنید.
3. برای پایگاه‌داده‌ی production، به‌جای SQLite از PostgreSQL استفاده کنید (`DATABASES` در settings.py).
4. `python manage.py collectstatic` را برای جمع‌آوری فایل‌های استاتیک اجرا کنید (اکنون از
   `core/static/core/` جمع‌آوری می‌شود) و از طریق وب‌سرور (Nginx) یا CDN سرو کنید.
5. برای مدیای آپلودی (تصاویر اعضا/اخبار/نمونه‌کارها/اسلایدها)، از یک storage backend مناسب (مثل S3) استفاده کنید.
6. پروژه را پشت Gunicorn/uWSGI + Nginx اجرا کنید.
7. کتابخانه‌های CDN داشبورد را در صورت نیاز به کار آفلاین، محلی‌سازی کنید.
8. رمز عبور کاربر نمونه‌ی `news-editor` (ساخته‌شده توسط `seed_data`) را در محیط production تغییر دهید یا حذف کنید.
9. **مهم — قبل از استفاده‌ی واقعی حتماً تست کنید**: ادغام CKEditor داخل مودال SweetAlert2
   (فایل `core/static/core/js/dashboard.js`، توابع `initCKEditor` / `syncCKEditorsToTextareas`)
   بر پایه‌ی ساختار HTML شناخته‌شده‌ی ویجت `django-ckeditor` (کلاس `django_ckeditor_widget` و
   attribute یا `data-config`) نوشته شده، اما چون این پروژه هرگز با نسخه‌ی واقعاً نصب‌شده‌ی
   کتابخانه اجرا نشده، حتماً پس از `pip install` واقعی، فرم افزودن/ویرایش عضو را در مرورگر
   امتحان کنید تا مطمئن شوید متن غنی درست ذخیره می‌شود.

## توسعه‌های پیشنهادی بعدی

- اتصال به API رسمی گمرک ایران برای داده‌ی واقعی HS Code.
- افزودن سامانه‌ی عضویت آنلاین با پرداخت حق عضویت.
- محدودکردن دسترسی «مدیریت کاربران» طوری که فقط superuser بتواند به کاربر دیگری دسترسی «users» بدهد (در حال حاضر هر کاربری با دسترسی «users» می‌تواند دسترسی کامل به کاربران دیگر هم بدهد).
- به‌روزرسانی سطرهای جدول در جای خود پس از افزودن/ویرایش/حذف با AJAX (در حال حاضر پس از موفقیت، صفحه رفرش می‌شود که ساده‌تر و پایدارتر است).
- افزودن قابلیت آپلود تصویر داخل CKEditor (`django-ckeditor` با `ckeditor_uploader`)؛ در حال حاضر فقط درج تصویر با آدرس URL پشتیبانی می‌شود.
